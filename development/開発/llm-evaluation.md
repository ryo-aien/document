# LLMの精度評価

精度評価とは、LLMが与えられた入力に対し「正しい」出力をどれだけ返せるかを、数値で定量化するプロセスです。一般に「正解が1つに定まる」タスク（QA、計算、コード生成テスト、RAGの正確性チェックなど）を用い、各指標をスコア化します。再現性の高い一連のベンチマークを自動スクリプトやCI/CDパイプラインに組み込み、モデル更新ごとに同条件で測定できるようにします。

## 精度評価がなぜ必要なのか

### 1. 仕様を満たしているか

**KPI未達:** FAQボットなら「正答率90%以上」といった合格ラインを満たしているか、数値で証明できなければリリース判断ができません。

**安全性保証:** 毒性・情報漏えいを防ぐフィルタが十分かどうかも、評価指標（toxicity scoreなど）で把握する必要があります。

### 2. 改善の方向性が定まらない

どのタスクで弱いのか（計算・推論・長文読解…）を可視化しないと、追加学習やプロンプト調整の優先度を決められません。

**ボトルネック特定:** Perplexityが低くても回答評価（MT-Bench）が悪ければ、生成ロジックではなくRAGのretrieval部分が問題――など原因切り分けが容易になります。

### 3. ステークホルダーへの説明責任

社内外のユーザー、法務・セキュリティ部門、顧客企業などに対し「どのレベルまで検証済みか」を示すエビデンスになります。

特にEU AI Actなど規制が進む領域では、テスト結果のログが必須となるケースも想定されます。

## LLMの代表的なユースケース

| ユースケース | 具体例 | 主な評価観点 |
|-------------|--------|-------------|
| **質問応答 (QA)** | FAQ応答、SQuAD形式 | 正確性、再現性、EM/F1スコア |
| **要約生成** | 契約書・議事録の要約 | ROUGEスコア、自然さ、情報保持率 |
| **翻訳** | 技術文書の多言語対応 | BLEU、METEOR、意味の保持 |
| **チャットボット** | カスタマーサポートなど | 応答の一貫性、関連性、有用性 |
| **自然言語生成 (NLG)** | アイデア生成、文書作成支援 | 自然さ、多様性、一貫性 |
| **分類** | テキストのスパム判定など | 正解率、F1スコア、混同行列 |
| **知識推論** | 常識・因果推論（例: HellaSwag） | 正答率、選択肢の整合性 |
| **文書検索+生成 (RAG)** | 社内ナレッジから回答生成 | 検索精度（Recall@k）、回答精度 |

## ユースケースの評価方法

| タスク種別 | 自動評価指標 | その他の評価方法 |
|-----------|-------------|-----------------|
| QA | EM, F1 | 人手評価、LLM評価 |
| 要約 | ROUGE, BERTScore | 人手評価（内容の過不足） |
| 翻訳 | BLEU, METEOR | 人手評価（文法・意味） |
| チャット | N/A（自動困難） | 人手評価、GPT-judge |
| 分類 | Accuracy, F1, ROC-AUC | Confusion Matrix |
| RAG | Retrieval Recall, Answer EM/F1 | 検索内容の可視化・レビュー |

## RAGの評価手法

RAGの評価手法は、検索（Retrieval）と生成（Generation）の2段階で行います。

| 評価対象 | 評価指標 | 内容 |
|---------|---------|------|
| **検索精度** | **Recall@k** | 検索結果（k件中）に正解が含まれているか（情報検索の正確性） |
| | **Precision@k** | 取得したk件のうち正しいものの割合（不要な文書が少ないか） |
| | **MRR（Mean Reciprocal Rank）** | 正解が何番目に出たかの逆数の平均（早く出るほど良） |
| | **Hit@k** | k件中に少なくとも1つ正解が含まれているか（0/1評価） |
| **生成精度** | **Exact Match（EM）** | 生成された回答が模範解答と完全一致か |
| | **F1スコア** | トークンレベルでの部分一致を考慮（EMのゆるい版） |
| | **ROUGE / BLEU** | 長文出力に対して参照文とのn-gram重複率などを計算 |
| | **BERTScore** | 意味的な類似度を埋め込みベースで評価 |
| | **LLM Judge** | GPT-4などで「どちらの回答が優れているか」を判定 |
| **全体の一貫性・有用性** | **人手評価** | 正確性、一貫性、自然さ、有用性などを人が主観評価 |

## 評価の具体的手順

### 1. ベンチマークデータセットの用意

「質問、文書コーパス、期待される」正解をセットにしたデータを作成。

例:
```json
{
  "question": "返品ポリシーは？",
  "expected_answer": "商品到着後30日以内なら返品可能です。",
  "relevant_docs": ["doc_id_3", "doc_id_7"]
}
```

### 2.検索部分の評価

入力質問から検索された文書が「relevant_docs」（関連ドキュメント）に含まれているかを「Recall@k」で評価。

実装にはFAISS, BM25, Elasticsearchなどの結果ログを活用。

### 3.生成部分の評価

生成された回答を「expected_answer」と比較し、EM/F1やROUGEを計算。

HuggingFace evaluateライブラリやseqeval, sacrebleuなどが使用可能。

### 4.LLMによる総合評価

LLM（GPT-4など）に複数回答を提示し、「どちらがより適切か」などを評価させる。

評価テンプレート例:
```
質問: ○○○
回答A: ...
回答B: ...
→ より正確な回答は？ 理由も添えて。
```

## 評価自動化のライブラリ/ツール

| ツール | 用途 |
|-------|------|
| `lm-eval-harness` | LLM評価のベンチマークツール。独自プロンプト評価にも使える |
| `evaluate` | Hugging Faceの評価ライブラリ。F1/ROUGEなど対応 |
| `Ragas` | RAG特化の評価ツール（retrieval + generation） |
| `Langchain Evaluation` | LLMを使った回答評価に対応 |
